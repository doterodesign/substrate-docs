A brand in Substrate is a directory containing a YAML config. That file is the only place you author brand identity — the pipeline reads it and emits solver inputs, style descriptors, and baked per-mode token files for every platform. There is no JSON config, no root-level config file, and no registration step: brands are discovered by scanning the brands directory.

## File layout

Two shapes are supported, and which one you get depends entirely on the directory structure.

<Tabs>
  <Tab title="Brand family">
    A family directory holds a shared `config.global.yaml`, and each sub-brand directory holds a `config.yaml` containing only its deltas. This is how the Delta, Stripe, Google, Descript, and DraftKings brands ship.

    ```
    src/brands/delta/
    ├── config.global.yaml      # shared foundation
    ├── booking/config.yaml     # deltas only
    ├── skymiles/config.yaml    # deltas only
    └── premium/config.yaml     # deltas only
    ```

    Each sub-brand becomes its own brand, with the merged slug `{parent}-{sub}` — `delta-skymiles`. See [Inheritance](/multi-brand/inheritance) for the merge rules.
  </Tab>
  <Tab title="Flat brand">
    A brand with no sub-brands is a single directory with a single `config.yaml`. Magic Patterns ships this way.

    ```
    src/brands/magic-patterns/
    └── config.yaml
    ```

    The slug is the directory name — `magic-patterns`.
  </Tab>
</Tabs>

<Note>
  **Keys are authored in kebab-case and normalized to camelCase at load.** `heading-family` becomes `headingFamily`, `duration-base` becomes `durationBase`, and so on throughout the schema. The exception is named-resource maps — `intents`, `gradients`, `ramps`, `materials`, `rampOutputs` — whose direct child keys are your own identifiers and round-trip verbatim one level deep. The scheme-track grammar keys (`scheme-end`, `scheme-track`, `from-intent`) also keep their kebab spelling at any depth, because the kernel consumes them that way. This rule holds for every config page in this section.
</Note>

## The required sections

Seven sections are non-optional. A config missing any of them is incomplete, and a config missing the required intents fails to load outright. Here is the shipped Stripe foundation (`src/brands/stripe/config.global.yaml`), trimmed to the required sections:

```yaml
intents:
  brand:
    hue: 277        # Stripe Indigo
    chroma: 0.268
  neutral:
    hue: 251        # cool-tinted neutrals
    chroma: 0.012
  danger:
    hue: 11
    chroma: 0.228

elevation:
  step-light: 0.015
  step-dark: 0.04
  sunken-step: 0.02

typography:
  heading-family: "'Sohne', 'Inter', system-ui, sans-serif"
  body-family: "'Sohne', 'Inter', system-ui, sans-serif"
  base-font-size: 1
  scale-ratio: 1.25

shape:
  radius-base: 6

motion:
  duration-base: 200
  easing: "cubic-bezier(0.25, 0.1, 0.25, 1)"

space:
  unit: 4

flexibility:
  scheme: true
  contrast: { min: 0.75, max: 1.5 }
  density: { min: 0.8, max: 1.3 }
  type-scale: { min: 0.9, max: 1.4 }
  motion: { min: 0, max: 1 }
```

<AccordionGroup>
  <Accordion title="intents">
    An **open map** of color intents. Only `brand` and `neutral` are required — the loader throws if either is missing. Every other intent is the brand's own choice, and there is no built-in-versus-custom split: a custom intent like `stripe-cyan` gets identical treatment to `danger`. Each intent carries `hue` (0–360) and `chroma` (0–~0.4); lightness is never authored, because the solver owns it. See [Color](/brand-config/color).
  </Accordion>

  <Accordion title="elevation">
    Lightness steps the solver applies to raised and recessed surfaces: `step-light` for the light end of the scheme axis, `step-dark` for the dark end, and `sunken-step` for recessed surfaces. Stripe keeps light-mode elevation subtle at `0.015` and lets dark mode carry more at `0.04`.
  </Accordion>

  <Accordion title="typography">
    `heading-family` and `body-family` are required; `mono-family` is optional. `base-font-size` is a number in **rem** (every shipped brand uses `1`), not a pixel string. `scale-ratio` is the modular ratio the continuous type scale raises to a power — 1.25 for Stripe and Magic Patterns, 1.2 for Delta. The optional `fluid` block (`rate`, `floor`, `ceiling`, `quantum`) and `density` block (`font-size-k`, `font-weight-k`) tune responsive and density-linked behavior. See [Typography](/brand-config/typography).
  </Accordion>

  <Accordion title="shape">
    `radius-base` in pixels. It is the base for the runtime-scaled `--radius`, so corner rounding tracks the density slider rather than being fixed. Delta uses `4`, Stripe `6`, Magic Patterns `12`.
  </Accordion>

  <Accordion title="motion">
    `duration-base` in milliseconds and `easing` as a CSS easing function. Both are required. Shipped values vary widely — Delta uses `75` with `linear`, Stripe `200` with a custom cubic-bezier. See [Motion](/brand-config/motion).
  </Accordion>

  <Accordion title="space">
    A single `unit` in pixels. All six shipped brands use `4`. There is no spacing ladder; this one unit is multiplied at each use site by the runtime density and scale factors. See [Spacing & Density](/brand-config/spacing-density).
  </Accordion>

  <Accordion title="flexibility">
    The brand's policy on how far users may move each preference axis. `scheme` is a boolean; `contrast`, `density`, `type-scale`, and `motion` each take `{ min, max }` bounds; the optional `effects` boolean gates visual effects. This is how a brand says "our users may go down to 0.8 density but no further" — the runtime clamps the sliders to these bounds.
  </Accordion>
</AccordionGroup>

## Optional sections

<AccordionGroup>
  <Accordion title="presets">
    Named tuning bundles over the continuous preference axes, in three open maps: `mode`, `density`, and `contrast`. Each level declares its position on the underlying slider — a mode level needs both `scheme` and `contrast-factor`; a density level needs `density-factor`; a contrast level needs `contrast-factor`. Level names are brand-defined, not an enum. Stripe's `presets.mode` block:

    ```yaml
    presets:
      mode:
        light:
          scheme: 0.02        # not pure white
          contrast-factor: 1.0
        dark:
          scheme: 0.74        # Brand Dark 900 — Stripe never uses pure black
          contrast-factor: 1.0
        dimmed:
          scheme: 0.55
          contrast-factor: 0.95
        high-contrast:
          scheme: 0.02
          contrast-factor: 1.3
        dark-high-contrast:
          scheme: 0.78
          contrast-factor: 1.3
      density:
        compact:
          density-factor: 0.85
        default:
          density-factor: 1.0
        comfortable:
          density-factor: 1.15
    ```

    A brand that omits `presets.mode` does not get those five modes — they are authored, not automatic.
  </Accordion>

  <Accordion title="gradients">
    An open map of named gradient recipes. Each has a `type` (`linear` or `radial`), geometry (`angle`, or `shape` and `origin`), and a list of `stops`. Unlike intents, a gradient stop **does** author `lightness` — it references an intent by name and pins a lightness and position:

    ```yaml
    gradients:
      aurora:
        type: linear
        angle: 120
        stops:
          - intent: brand
            lightness: 0.50
            at: 0
          - intent: stripe-pink
            lightness: 0.72
            at: 100
    ```
  </Accordion>

  <Accordion title="ramps">
    An open map of ramp recipes that generate stepped opaque scales from an intent — for Tailwind-style palettes and DTCG export. A recipe names its source `intent`, a list of `steps` (pure labels, lightest to darkest), and optionally `lightest-l`, `darkest-l`, `gamut`, `outputs`, and `sample`. The related top-level `color` key holds ramp orchestration (`ramps` defaults and `ramp-outputs` formats) — it is not where you put brand colors.
  </Accordion>

  <Accordion title="materials">
    An open map of named filter compositions — blur, saturate, tint, noise — applied through `data-mode`. Paired with the optional `effects: { blur-unit: … }` block that sets the base blur unit.
  </Accordion>

  <Accordion title="system">
    A free-form map of system-config overrides, deep-merged over Substrate's defaults for this brand only. Use it to change engine-level behavior a brand needs to diverge on, rather than forking the engine.
  </Accordion>
</AccordionGroup>

## What the loader does with it

Discovery is a directory scan. For each directory under the brands root, the loader checks for `config.global.yaml` (family) or `config.yaml` (flat), parses the YAML, normalizes the keys, deep-merges family and sub-brand layers where both exist, and stamps the `slug` from the directory structure. That slug is what appears in generated CSS as `[data-brand="delta-skymiles"]`.

Two validations run at load. The intent roster must contain `brand` and `neutral`, or the load throws a missing-required-intent error. Any intent using scheme-track grammar is desugared and validated, including reference cycles and unknown intent names.

<Warning>
  Substrate has no build verb and no per-brand build flag. Generation runs as `npm run generate` in the engine checkout, which regenerates every brand. The `substrate` CLI is a consumer-side onboarding tool with the verbs `init`, `add`, `upgrade`, `adopt`, `setup`, and `artifact`.
</Warning>
