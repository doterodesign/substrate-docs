Substrate is a computed design system framework built by [Unknown Creatives](https://unknowncreatives.com), a design systems studio. It exists because static token libraries — the spreadsheets, Figma variables, and JSON files that define a fixed color ramp or a hand-tuned type scale — cannot describe the full range of users who interact with your product. Substrate replaces that static model with a declarative one: you describe what your brand *intends*, and the system derives every token value mathematically, for every user context, every time you build.

## The Problem With Static Tokens

Static design tokens store a value. `color-primary-500: #1A7F5A`. That value was probably chosen to look good in light mode, on a calibrated display, by someone with standard color vision. It may pass a WCAG 2.x contrast check against a white background. But it says nothing about:

- **Dark mode** — the same hue at the same lightness often fails contrast checks on dark surfaces.
- **Dimmed mode** — users on OLED displays or in low-light environments benefit from reduced luminance, which a static ramp doesn't accommodate.
- **High-contrast mode** — users with low vision need foreground values that achieve significantly higher contrast, not a slightly bolder version of the same token.
- **Color vision deficiency (CVD)** — a palette designed around green and red as signal colors fails a large portion of users without a CVD-aware remap.

Teams that care about these users end up maintaining parallel token sets — a light ramp, a dark ramp, a high-contrast ramp — all authored by hand, all drifting apart the moment the primary color changes.

## Substrate's Approach

Substrate replaces fixed token values with *intent*. You declare the following in a single `substrate.config` file:

- **Color** — a primary hue and chroma expressed in OKLCH
- **Space unit** — the base unit for your spacing scale (e.g. `4px`)
- **Type size unit** — the base unit for your type scale (e.g. `16px`)
- **Scale ratio** — the multiplier between steps on both scales (e.g. `1.25`)
- **Motion unit** — the base duration for animation and transition tokens (e.g. `100ms`)

From those inputs, Substrate calculates every downstream token value at build time. Color ramps are interpolated across the OKLCH color space, which produces perceptually uniform steps. Foreground colors are never hand-picked — they are mathematically derived by the APCA (Advanced Perceptual Contrast Algorithm) contrast solver, which finds the exact lightness value that achieves your target contrast against any given background.

## Key Benefits

<AccordionGroup>
  <Accordion title="Always-accessible contrast">
    Every foreground token in every mode meets your contrast target by construction. You don't check contrast after authoring — the solver produces accessible values and nothing else.
  </Accordion>
  <Accordion title="Automatic mode generation">
    A single brand config produces five complete token sets: `light`, `dark`, `dimmed`, `high-contrast`, and `high-contrast-dark`. You don't maintain parallel files.
  </Accordion>
  <Accordion title="Multi-brand from a single config model">
    Multiple brands in one system share the same mathematical model. A new brand supplies its own color, space-unit, and scale-ratio — all accessibility behavior is inherited automatically.
  </Accordion>
  <Accordion title="Platform-agnostic output">
    Every build target — Web (CSS custom properties), iOS (Swift constants), Android (Kotlin objects) — receives the same logical token values expressed in the native format for that platform.
  </Accordion>
</AccordionGroup>
